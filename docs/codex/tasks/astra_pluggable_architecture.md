# webClx 可插拔架构与动态链接库评估

评估日期：2026-09-16。源码基线：`adf8c5c`，包版本：`1.8.16`。
本文是架构建议，不表示插件运行时已经实现；本次仅修改文档，未进行性能实测或跨平台构建。

## 1. 结论

**本项目适合渐进式可插拔化，但不适合直接把主要业务模块全部改成动态链接库。**

推荐组合是：**核心静态链接 + 内部 crate 接口化 + 外围进程插件；确有性能收益时再增加少量 C ABI 动态库。**

- 如果目标是代码易维护、职责清晰、多人开发：继续拆 workspace crate 即可，不需要动态装载。
- 如果目标是功能按需启用、裁剪发行包：增加 Cargo feature 与运行时功能开关。feature 决定编译内容，运行时开关只决定是否启用。
- 如果目标是扩展独立发布、升级时不重启主服务：优先采用独立进程插件。
- 如果目标是低延迟调用已有原生计算库：采用 `cdylib` 和稳定 C ABI，但先测量调用频率、数据复制与 IPC 开销。
- 如果目标是运行受限的小型转换程序：后续可评估 WASM；当前不必同时建设两套插件运行时。

模块化、动态链接和热更新是三个不同目标。把 `mod` 改成 `.so` 不会自动解决状态耦合，也不会自动获得可靠热卸载。

## 2. 当前架构证据

| 代码入口 | 已观察到的结构 | 对方案的影响 |
| --- | --- | --- |
| [Cargo.toml](../../../Cargo.toml) | 根包及 6 个 workspace crate；未声明插件 `cdylib` 或插件加载依赖 | 已有源码级模块边界，尚无通用运行时插件机制 |
| [main.rs](../../../src/main.rs) | `AppState` 集中持有设置、认证、代理、FRP、终端、Agent 等 manager；启动时创建后台 runner | 直接导出业务函数会把共享状态、锁和生命周期带进 ABI |
| [routes/mod.rs](../../../src/routes/mod.rs) | 领域 Router 静态组合，集中应用认证、fallback 与压缩 | 适合保留宿主网关，在一个固定路由下分发扩展请求 |
| [settings.rs](../../../src/settings.rs) | HTTP handler 调用 `settings_core`，转换响应及错误 | 是“业务 crate + 宿主适配层”的现成模板 |
| [crates](../../../crates) | `api_catalog_core`、`auth_core`、`codex_proxy_core`、`runtime_paths_core`、`settings_core`、`terminal_core` | 应复用已有拆分，不另起一套同义 core |
| [terminal_core](../../../crates/terminal_core/src/lib.rs) | 包含恢复归档模型、解析和规则等；实际终端管理仍在 `src/terminal/` | crate 名称并不代表已经拥有独立终端服务边界 |
| [Agent 工具分派](../../../src/agent.rs) | `execute_tool` 按工具名匹配；工程工具接收 `AppState` | 可引入扩展工具注册，但先拆出最小上下文 |
| [协议转换](../../../src/upstream_proxy/transform.rs) | 转换逻辑已从代理编排中提取 | 适合作为纯逻辑接口试点，网络路由和凭据仍留宿主 |
| [编译路由](../../../src/routes/operations.rs) | 编译、部署、回调由固定 API 接入 | 插件可以提供部署适配器，但不应另建绕开现有队列的执行入口 |
| [模块拆分约定](project-module-slimming.md) | 前端使用有顺序依赖的经典脚本与 manager | 当前拆脚本不等于 UI 插件化，需要额外设计注册和销毁契约 |

本次检视的是架构入口与候选边界，不是逐函数依赖审计。尚无数据证明构建时间、内存占用或吞吐瓶颈由静态链接造成。

## 3. 技术路线比较

| 方案 | 独立发布 | 故障隔离 | 调用成本 | 维护成本 | 本项目定位 |
| --- | --- | --- | --- | --- | --- |
| workspace crate / 默认静态链接 | 随主程序发布 | 同进程 | 低 | 低 | 第一阶段主线 |
| Cargo feature | 需重新构建 | 同进程 | 低 | 中，需覆盖组合 | 精简发行包，可选 |
| Rust `dylib` / Rust ABI | 强依赖构建环境匹配 | 同进程 | 低 | 高 | 不作为长期插件契约 |
| `cdylib` + C ABI | 可独立发布，按平台产物匹配 | 同进程 | 低，仍可能复制 | 高 | 小型可信原生模块 |
| 独立进程 + 版本化 RPC | 可以 | 可隔离崩溃，资源隔离另做 | 序列化与 IPC | 中 | 外围扩展首选 |
| WASM / 组件接口 | 可以，受运行时契约约束 | 有运行时隔离能力 | 需实测 | 中高 | 后续纯转换扩展候选 |

Rust 默认 ABI 没有面向任意编译器版本的稳定保证。`pub trait`、`Box<dyn Trait>`、`String`、`Vec`、`Arc`、Tokio future 或 Axum Router 都不宜直接跨动态库边界。`repr(C)` 只规定所标记类型的布局，并不会把其内部 Rust 对象自动变成稳定 ABI。

拆 crate 可能改善增量开发，但 release 的链接或 LTO 仍可能成为瓶颈；不能承诺“插件化后编译必然更快”。

## 4. 哪些模块适合拆

| 模块 | 建议形态 | 顺序与原因 |
| --- | --- | --- |
| 特定应用诊断，如 `cymusic_diagnostics` | 进程插件候选 | 第一试点：业务独立；先盘点上传、存储、公开接口的实际权限契约 |
| 新增只读报告、格式解析、导出工具 | 内置接口实现，随后进程插件 | 第一试点备选：副作用少，容易验证 RPC 与升级流程 |
| Agent 外部工具 | 进程插件，经宿主工具注册表接入 | 第二阶段；工具声明、权限、结果大小和取消需统一 |
| 部署目标适配器、产物解析 | 队列调用进程插件 | 第二阶段；任务身份、审计、回调和幂等由宿主维持 |
| FRP 管理集成 | 可选进程插件 | 较晚；现有进程所有权、配置保存与重启行为需完整迁移 |
| 纯 JSON 协议转换 | 优先静态 crate；可选 C ABI / WASM | 边界较好，但序列化成本可能抵消动态库收益 |
| 终端 PTY/tmux、WebSocket 输出链路 | 核心静态模块 | 长生命周期、顺序和延迟敏感；不是首批热插拔对象 |
| 认证、用户身份、真实配置写入、预设事务 | 核心静态模块 | 必须保留权威来源和统一操作边界 |
| 编译协调器、宿主启动、插件注册器 | 核心静态模块 | 扩展失败时仍要能诊断、禁用和回滚 |
| 浏览器页面扩展 | 声明式贡献；后续独立页面 | 与后端插件分开设计，避免共享全局变量 |

`auth_core` 等已经独立成 crate 的模块仍可留在核心。是否做插件由生命周期和发布需求决定，不由目录是否独立决定。

## 5. 推荐目标结构

以下名称和目录是拟议结构，现有六个 core crate 保留。

```text
webclx 宿主
  ├─ HTTP 认证、用户身份、工作区访问控制
  ├─ 终端服务、配置事务、编译协调器
  ├─ 内置功能注册表
  └─ 插件管理器
       ├─ 清单验证、协议协商、能力授权
       ├─ RPC 分派、任务超时、输出限额
       └─ 插件进程 A / 插件进程 B

crates/webclx_extension_protocol/   # DTO、错误码、版本；不依赖 Axum/AppState
crates/webclx_extension_host/       # 注册、传输、生命周期；通过窄接口调用宿主
plugins/<id>/<version>/            # 独立版本产物与 manifest
```

依赖方向为宿主 → 插件管理器 → 协议；插件 → 协议。业务 crate 不反向依赖根二进制。不要创建包揽全部 manager 的新“公共上下文”来替换 `AppState`，那只是搬迁耦合。

宿主保留 `/api/extensions/{id}/...` 的固定受保护入口，运行时查注册表再分派。插件不返回 Axum Router，不重建全站 Router，也不自行绕过宿主认证。确需公开接收诊断上传时，由宿主明确注册和审核对应公开能力，保持旧接口的认证、限流和存储语义。

## 6. 首版进程插件契约

### 6.1 清单

下面是设计样例，不是当前可用配置。

```json
{
  "id": "report-export",
  "version": "0.1.0",
  "protocol_major": 1,
  "protocol_minor": 0,
  "transport": "stdio-jsonrpc",
  "entry": "bin/report-export",
  "target": "x86_64-unknown-linux-gnu",
  "capabilities": ["reports.render"],
  "config_schema_version": 1
}
```

安装时检查 ID 唯一性、目标平台、文件哈希和入口真实路径是否位于插件版本目录；版本目录不可由上传文件路径任意穿越。宿主对照自己的授权配置授予能力，不能把清单自报能力直接当成许可。能力集合首版从只读、无凭据接口开始。

### 6.2 传输与接口

首版采用子进程 stdin/stdout 上的 JSON-RPC 2.0，使用一行一条 UTF-8 JSON 的明确分帧；stdout 专用于协议，stderr 用于受限日志。Windows 与 Linux 使用相同消息契约，但各自发布原生可执行文件。

最小方法：

- `initialize`：交换协议版本、插件版本、宿主授予的能力和配置版本。major 不兼容时不激活；minor 通过能力协商使用。
- `invoke`：携带请求 ID、方法、参数与截止时间。身份由宿主已验证的请求上下文关联，插件回报身份不作为授权依据。
- `cancel`：取消指定请求；规定取消确认与完成响应竞争时的处理方式。
- `health`：返回就绪状态与插件自身错误，不访问全部宿主配置。
- `shutdown`：停止接收新任务，结束在途任务并清理资源。

长任务先返回 job ID，再通过带序号的通知发送进度；任务取消、终态和错误具有明确字段。二进制/大文件通过受控文件句柄或限定存储接口交换，不塞进无限长 JSON。

初始建议限额：单帧 1 MiB、单插件并发 4、普通调用 30 秒；这些是待验证默认值，不是已测得的最优参数。长任务需独立限时。读取器在缓冲增长时执行上限检查，写队列有界，慢消费者触发背压或明确错误。

有副作用的 `invoke` 增加幂等键。插件断连后的“结果未知”不能自动当失败重试；先按 job ID 查询或由任务所有者对账。配置、文件写入和部署只由获得授权的宿主服务执行。

### 6.3 生命周期、升级与存储

状态机：`discovered → validated → starting → ready → draining → stopped`，任一步失败进入 `failed` 并记录原因。重启使用有上限的退避策略；连续失败后保持停用，避免无限拉起。

升级先安装到新版本目录，握手和健康检查通过后切换新请求；旧进程完成在途请求再退出。Windows 不覆盖运行中的 exe/DLL。若插件要求独占资源，则使用短暂排空再启动，明确报告停顿，不承诺零中断。

插件私有数据按 ID 单独存储，由插件负责其 schema；宿主配置和会话数据继续由宿主负责。破坏性迁移前保留兼容备份；新版已写入不兼容数据时，回滚需要恢复数据或反向迁移，切换二进制不等于完整回滚。

插件进程单独运行只能提供崩溃隔离，不能自动限制文件、网络或凭据访问。首版仅装载受信任插件；若开放不受信任扩展，需要另行落实独立 OS 用户/容器或 WASM 能力沙箱。插件启动机制不修改终端和 Codex/Claude 的环境、配置路径或启动身份。

## 7. 如果确实要做动态链接库

只为边界稳定、同步、短调用的可信模块建立 `cdylib`，使用 `libloading` 等宿主加载设施。库名称按平台发布为 `.so`、`.dll`、`.dylib`，并记录架构、操作系统与运行库基线。

最小 ABI 可以按以下 C 头文件方向设计；这是接口草案，不是已完成的 SDK：

```c
#include <stdint.h>
#include <stddef.h>

typedef struct {
    uint32_t abi_major;
    uint32_t struct_size;
    int32_t (*create)(void **instance);
    int32_t (*invoke)(void *instance,
                      const uint8_t *input, size_t input_len,
                      uint8_t *output, size_t output_cap,
                      size_t *required_len);
    void (*destroy)(void *instance);
} WebclxPluginV1;

/* 插件内静态表，库保持加载期间有效 */
const WebclxPluginV1 *webclx_plugin_entry_v1(void);
```

配套约束必须一起定义：

1. Rust 使用 `#[repr(C)]` 表和 `extern "C"` 函数；edition 2024 导出符号使用对应 unsafe attribute 语法。宿主先核验 major 和 `struct_size`，再读取支持的函数指针。
2. 状态由插件 `create` / `destroy` 成对管理；输入只借用到调用结束，输出由宿主分配。插件不得保存这些 buffer 的指针。
3. 返回码规定成功、缓冲不足、输入无效、内部错误；缓冲不足返回所需长度且不写越界。首批仅接受纯函数式操作，查询长度/重试不得产生重复副作用。
4. 单实例默认串行调用；线程安全、可重入和调用线程要求写入契约。不要让 Rust future、锁、引用或 trait 对象跨 ABI。
5. 插件入口处理可捕获的 Rust panic，禁止 unwind 穿越 ABI。`panic=abort`、段错误与内存破坏仍可终止宿主，错误码没有进程隔离能力。
6. 首版不提供运行中卸载：装载句柄活到宿主退出，升级后重启宿主。将来若做卸载，必须证明所有实例、线程、回调和函数指针引用已清理，而不只是请求计数为零。
7. 动态库单独构建及发布；保持已验证工具链约束，C ABI 也仍需按 OS、架构和运行库测试。Nightly 更新不等于 ABI 兼容性验证。

如果业务需要异步网络、长连接、大量宿主回调或独立 Tokio runtime，优先采用进程协议，不扩张这个 ABI 承担整个服务器。

## 8. 前端扩展边界

第一版只接受声明式菜单、表单与操作定义，由现有前端渲染并调用受保护的扩展 API。禁用插件时同步移除入口，并正确处理已打开页面。

未来完整 UI 插件应定义 `mount(context)` / `unmount()` 和版本化 UI API，清理事件、定时器与订阅。可信同源 JS 具有页面权限，manager 模式不提供安全隔离；不受信任 UI 需独立来源或 sandbox iframe，并对消息来源和允许操作逐项验证。

遵循当前静态资源唯一实体目录规则；插件目录作为单独、受限的资产来源，不复制出第二套主站 `static`。现有经典脚本继续保留，不为插件试点顺带全面切换 ES module。

## 9. 分阶段落地与验收

| 阶段 | 具体改动 | 完成标准 |
| --- | --- | --- |
| 0：确认目标与基线 | 记录编译耗时、核心请求延迟、内存、发布频率；选一个无副作用报告工具试点 | 明确要解决独立发布还是性能，不混用指标 |
| 1：先做内置接口 | 提取 DTO 与最小业务上下文，增加内置实现注册表；沿用现有 crate | 原 API 和结果保持一致，依赖不回指根 `AppState` |
| 2：进程运行时 | 实现清单、协议、宿主分派、生命周期与限额；试点外置 | 插件缺失、崩溃、超时均不影响终端和登录；错误可追踪 |
| 3：发布和升级 | 版本目录、健康检查、排空、回滚、数据版本与能力授权 | 在途任务不重复执行；插件可独立更新；旧版本可恢复 |
| 4：第二个扩展 | 迁移专用诊断或新增 Agent 工具，验证接口复用 | 不为每个扩展新增专用宿主后门接口 |
| 5：按数据优化 | 仅在 IPC 或计算确为瓶颈时试验 C ABI/WASM | 同输入实测收益覆盖复杂度与跨平台成本，否则保留原方案 |

首版范围控制在一个插件、一个协议版本和一种传输。暂不实现插件市场、依赖自动求解、任意 UI 脚本注入、核心终端热卸载。

验证至少覆盖：

- 内置实现与插件实现对同一输入的输出及错误一致；旧 API 路径、状态码和数据格式兼容。
- 协议 major 不匹配、重复 ID、畸形帧、超大输出、启动卡住、请求中崩溃、取消竞争、慢消费者、主服务退出。
- 任务结果未知时不重复执行；升级期间请求排空；数据迁移失败和旧版本回滚。
- Linux/Windows 插件启动、退出及整个进程树清理；测试启用 kill-on-drop 和 RAII guard，进程操作使用短超时。
- 新会话、resume、fork、预设切换后再启动，确认仍由真实当前配置决定 model/provider；不得借插件化改变 direct/中继边界。
- UI 禁用和重载无悬挂监听器；无插件安装时登录、终端、编译队列照常工作。

实施时经现有 webClx compile/deploy API 执行相关检查，按队列回调继续验收；持久子进程测试的整条命令加 `timeout --signal=KILL`。文档阶段不需要提交编译或重启任务。

## 10. 建议决策

现在批准“接口化和单个进程插件试点”最有价值。沿用现有六个 crate，先减少业务对全量 `AppState` 的依赖，再实现版本化进程协议。动态库保留为特定纯计算需求的后续选项，不作为整体重构的默认方向。

本方案不重新定义项目既有的终端、用户身份、配置权威和预设恢复规则；若既有文档之间有冲突，应在相应专题独立澄清，不在插件运行时另造一套语义。
